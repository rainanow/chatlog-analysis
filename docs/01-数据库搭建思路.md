# 交接文档 · 聊天数据库搭建

> 生成时间：2026年9月17日 02:16
> 议题：如何把 2-3 年、每天聊、约 20MB 的聊天记录，整理成可索引、可回溯的结构化数据库
> 状态：**方案已定型，尚未开工**

---

## 一、背景与目标

### 手上的材料

| 项 | 情况 |
|---|---|
| 时间跨度 | 2-3 年 |
| 频率 | 每天聊 |
| 体量 | **约 20MB txt**（估算 600-700 万字符，10-20 万条消息） |
| 现有格式 | **txt / html / json / excel 都有**（多格式并存） |
| 母题 | 这段记录来自一段长期关系，想起的是"事件、情绪、变化" |

### 真正要解决的问题

不是"把记录存起来"——记录本来就在。要解决的是：

1. **回忆**：想某件事时不用翻原文
2. **看演变**：某个话题半年、一年里怎么变的
3. **不失真**：不能因为整理而丢掉细节

### 目标产物

```
原始记录（只读，永久保留）
      ↓
事件索引   ← 一行一条，回答"那天发生了什么"
主题索引   ← 一个话题一段，回答"这件事怎么变的"
悬置项     ← 提了没解决的事，只增不减
```

## 二、关键判断（这轮讨论的核心结论）

### 判断 1：20MB 不能按"分段逐段读"的方式处理

**为什么：** 20MB 分 100 段，每段仍有 5-6 万字符。逐段让 AI 建索引，时间成本不可接受。这不是上下文容量问题——**中间产物落盘后不占上下文**——纯粹是工作量问题。

**结论：必须先筛选，再整理。** 见判断 2。

### 判断 2：两三年每天聊的记录里，大部分内容不值得进索引

日常寒暄（"吃饭了""晚安""哈哈哈哈"）占比可能高达 **80%**。把它们全塞进索引，等于索引本身变成了噪声。

**结论：先用脚本粗筛，把高信息量的部分捞出来，再对筛出的内容建索引。**

### 判断 3：全量建索引的性价比，取决于你是否长期回看

| 目标 | 建议做法 | 工作量 |
|---|---|---|
| 只想找回某几件事 | **别建索引，直接搜关键词** | 快 |
| 想看清某几个话题的演变 | 关键词筛出相关段落 → 只整理这些 | 中等 |
| 想全面梳理两三年 | 走完整流程 | **几小时起** |
| 想长期持续用 | 上 ChatLab 建库 | 一次性投入 |

**先想清楚要哪个，再动手。** 两年记录里真正会回看的，可能就二三十件事。

### 判断 4：总原则——不要让超长记录全靠上下文扛

- 先分段，再喂
- **每段处理完立刻落盘**（文件是硬盘，不占上下文）
- 最后汇总时读的是索引，不是原文

这样无论记录多大，**上下文里同时存在的永远只有"一段原文 + 一份索引"**。

## 三、技术选型

### 3.1 格式选择

**结论：原始记录用 txt 存原文，整理结果用 json/xlsx 存。**

| 格式 | 处理难度 | 结论 |
|---|---|---|
| **txt** | 最顺，直接读 | 原文首选，微信导出默认格式 |
| **json** | 很顺，代码解析 | **最优**——有结构，不用猜格式 |
| **excel** | 中等 | 适合最终成品（要自己筛选排序时） |
| **html** | 最麻烦，要剥标签 | 只在仅有网页导出时用；**且容易出静默错误**（被样式隐藏的消息剥完标签看不出来） |

**关键原则：**

- 原文是只读的 → txt 最稳，不会因软件版本变化打不开
- 结果是反复查的 → json 方便代码处理，xlsx 方便人看
- **不要把原文转成 excel 图方便**——单元格长度限制会让长段落换行全乱

**关于多格式并存：**

手上有 txt/html/json/excel 四种，是好事也是坑。json/excel 可能藏着 txt 缺失的结构信息（精确时间戳、引用回复），但**不同格式的同一段记录可能对不上**（时间戳精度、昵称、表情处理都不同）。

**建议：先只用一种格式（优先 json），其他作为补充，别一上来就合并。**

### 3.2 工具选型

#### 已排除：ChatLog（sjzar/chatlog）

**这个工具已下架，不要使用。**

2025年10月20日，作者收到微信官方函件，认定核心功能存在合规风险，**移除了全部代码与提交历史**，仓库现在只剩一份说明文件。作者明确建议：本地若存有旧版本，请及时删除。

⚠️ **网上大量教程（CherryStudio 配 MCP、导出微信记录等）均基于此项目，全部已过期。**

#### 推荐：ChatLab（hellodigua/ChatLab）

| 项 | 情况 |
|---|---|
| 形态 | 桌面应用（Electron）+ CLI |
| 平台支持 | WhatsApp、LINE、QQ、Discord、Instagram、Telegram、iMessage、Google Chat、**微信** |
| 数据存储 | 全本地，原始对话不上传 |
| 查询方式 | SQL + AI Agent（24+ Function Calling 工具） |
| 可视化 | 活跃度趋势、时间分布、互动频率、成员排行 |
| 性能 | 百万条消息级，流式解析 + 多线程 |
| 协议 | AGPL-3.0，免费开源 |
| 官网 | chatlab.fun |
| 活跃度 | 7.3K star，最后提交 2026年9月（8天前发版） |

**架构**：五段式流水线——格式检测 → 流式解析 → 本地持久化 → SQL + AI 查询 → 可视化。核心亮点是**跨平台格式归一化**。

**但必须清醒认识到它的边界：**

| 需求 | ChatLab 能否满足 |
|---|---|
| 检索某句话 | ✅ 完全够用 |
| 看活跃度、时间分布 | ✅ 现成图表 |
| "那天发生了什么" | ⚠️ 只能靠搜关键词，**事件要自己定义** |
| 情绪变化趋势 | ⚠️ 给的是一次性结论，**不是纵向时间线** |
| 话题首现/消失 | ❌ **要自己写 SQL 或建表** |

> **一句话：ChatLab 是个数据库，不是时间线。**

#### 其他路线

- **自建**：sqlite + 简单脚本，自己建事件表和主题表。ChatLab 的价值就在于把它封好了
- **换平台**：Telegram / Discord 原生导出是 JSON，最规整。但手上是微信记录，此路不通

## 四、执行方案

### 推荐路线：两段式

```
第一段：ChatLab 干重活（导入、建库、检索、统计）
          ↓
第二段：AI 干细活（导出时间段 → 纵向整理事件与情绪）
```

**为什么必须两段：** ChatLab 的 AI 给的是**一次性分析**，不会累积索引。而"事件—情绪—变化"的纵向追踪，仍然得靠对话式整理。

### 流程步骤

#### 第一步：结构体检（先做这个，成本最低）

**不要一上来读全文。**

只读开头约 2000 行，产出"结构体检报告"：

- [ ] 格式是否统一（**两三年里导出工具可能换过，格式大概率会变**）
- [ ] 日期 / 说话人的标记方式
- [ ] 是否混入系统消息、广告、表情占位符
- [ ] 时间跨度确认
- [ ] 消息量估算

**目的：万一是烂格式，不至于白忙一场。**

#### 第二步：脚本粗筛

用代码捞"高信息量"的行，而不是逐条读。筛选信号：

- 包含关键词（离别、吵架、生病、工作、搬家……）
- 消息长度超阈值（长消息通常有内容）
- 消息量突增或突降的时间点（异常点）
- 深夜时段消息（情绪浓度通常更高）

**预期效果：筛完可能只剩 10-20%**，量级大幅下降。

#### 第三步：对筛出的内容分段建索引

- 用脚本切分（**切点要落在消息边界，不能把一条消息劈成两半**）
- 逐段处理，**每段处理完立刻落盘**
- 每段只做三件事：
  1. 追加几条事件索引
  2. 更新涉及到的主题索引
  3. 记下本段中**没解决的事**

#### 第四步：汇总校验

- 核对**每个分段是否都被覆盖**（防止中段遗漏）
- 输出时间段清单，检查有无断档

## 五、索引设计规范

### 5.1 四个必选维度

| 维度 | 为什么必须 | 记什么 |
|---|---|---|
| **日期** | 唯一的锚点 | 精确到天即可 |
| **事件** | 回忆的主体 | 一句话，别写长 |
| **情绪** | 单次对话里最没用，长期里最有用 | **必须是封闭词表** |
| **变化** | 长记录独有的价值 | 相对上一次，什么变了 |

> ⚠️ **情绪字段必须封闭化**，比如只用：`低 / 平 / 好 / 焦虑 / 亢奋`。
> 如果每处都写"有点难受""还行吧""复杂"，三个月后**根本无法检索、无法统计**。
> **这是最常见的失败点。**

### 5.2 两层索引

**事件索引**（一行一条，主键是日期）

```
09.17 | 抽卡受挫 | 低 | 首次提到设备问题
09.24 | 换手机计划搁置 | 平 | 家庭因素首次出现
```

**主题索引**（一个话题一段，主键是话题）

```
话题：设备
09.17 首次提出"设备拖累"
10.05 转为自嘲"没苦硬吃"
11.20 不再提，换了新话题
```

- 事件索引回答「**那天发生了什么**」→ 原料
- 主题索引回答「**这件事怎么变的**」→ 结论

**只做前者，三个月后还得自己串；只做后者，会丢细节。两个都要。**

### 5.3 四个高价值附加字段（长记录特有）

- **首现标记**：某话题第一次出现的时间
- **消失标记**：早期常提、后来再也不提的事。**比首现更值得注意**
- **悬置项**：提了但双方都没展开的事
- **未解决的循环**：反复出现但始终没解决的，标累计次数

### 5.4 别做的事

| 别做 | 原因 |
|---|---|
| 每段都写详细总结 | 三个月后你有 50 份总结，等于没有 |
| 情绪用自由描述 | 无法检索、无法统计 |
| 只按时间线索引 | 时间线是原料，不是结论 |
| 追求完整覆盖 | 日常寒暄会稀释信号 |

### 5.5 落地文件结构

```
index_events.md    ← 事件索引，一行一条，持续追加
index_topics.md    ← 主题索引，一个话题一段，持续更新
open_loops.md      ← 悬置项，只增不减（解决后划掉）
```

这套结构的好处是**增量维护**——新材料进来只追加，不用重写。
