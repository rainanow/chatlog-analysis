# 聊天记录处理方法（通用版）

> 适用：把任意 QQ / 微信 聊天记录导出（JSON）转成可检索数据库，
> 然后用「锚点 + 扩读 + 回扫」的方式做长期追踪分析。
> 本套工具不包含任何具体数据，拿到自己的 JSON 即可使用。

---

## 一、你需要准备什么

| 项 | 说明 |
|---|---|
| **一份导出的 JSON** | 推荐用 [QQChatExporter](https://github.com/shuakami/qq-chat-exporter)（V5 版），免费开源 |
| **Python 3.8+** | 只需标准库，无需 pip 安装任何东西 |
| **磁盘空间** | JSON 大小的 2 倍左右（原始 + 数据库） |

**关于微信：** 曾广泛流传的 `ChatLog`（sjzar/chatlog）项目**已于 2025-10-20 下架**，网上所有基于它的教程都已失效。
微信记录导出目前没有同等成熟的免费方案，需自行评估合规风险。

## 二、四步跑通

```bash
# 1. 把导出的 JSON 放到一个目录，重命名为 chat.json
#    再把 tools/ 下的 3 个 .py 复制到同一目录

# 2. 导入数据库（约 5 秒 / 100MB 数据）
python3 import_db.py                       # 默认读 ./chat.json，写 ./chat.db
python3 import_db.py 别处/xx.json 别处/xx.db   # 也可以显式指定路径

# 3. 固化你的数据指纹（首次必做）
python3 verify.py --init

# 4. 看全貌
python3 query.py top
python3 query.py peaks
```

**第 3 步是关键。** `verify.py --init` 会把当前数据的全部关键数字存进 `fingerprint.json`，
之后任何一次分析中引用的数字，都可以用 `python3 verify.py` 复核。

> **关于数据库路径**：`query.py` 默认读脚本同目录下的 `chat.db`。
> 如果数据库在别处，用环境变量指定：
> ```bash
> CHAT_DB=/path/to/chat.db python3 query.py top
> ```

## 三、为什么要这么做

### 3.1 为什么不直接看 JSON

| | JSON | SQLite |
|---|---|---|
| 每次全量扫描 | 8~10 秒 | 1~3 秒 |
| 按日/按人/关键词查 | 每次重扫 | 毫秒 |
| 反复迭代分析 | 越做越慢 | 恒定 |

几十万条记录做长期分析，**转库不是可选项**。

### 3.2 为什么不全量索引

30 万条里 **98% 是日常闲聊**（"吃了没""上课了""哈哈"）。

全量打标签的投入产出比极低，而且**你自己也读不完**。
正确做法是：**锚点 + 扩读 + 回扫**，永远只处理高价值片段。

### 3.3 为什么必须核对数字

这是本流程里最容易被跳过、也最致命的一步。

**真实案例**：我曾在分析中写下"某字段只有 41 条，与统计块的 2,341 条对不上"，
并据此判断"数据质量有问题"。复核后发现——**该字段实际就是 2,341 条，完全一致**。
我的 41 是用错字段路径数出来的。

> **一个错误的数字，会生成一个错误的结论，然后污染所有引用它的人。**

所以：**任何"发现异常"的判断，必须附可复现的统计代码。**

## 四、核心方法：锚点 + 扩读 + 回扫

### 步骤 1 · 找锚点

用 `query.py` 跑这几条命令，异常值就是锚点候选：

```bash
python3 query.py peaks          # 单日/单月极高值
python3 query.py silent 3       # 超过 3 天的沉默断点
python3 query.py top            # 全库概览
```

| 优先级 | 锚点类型 | 意义 |
|---|---|---|
| **P0** | 报告量的突变点 | 关系模式变化 |
| **P0** | 长消息密集日 | 深度沟通 |
| **P1** | 长沉默后重启 | 有事件发生 |
| **P1** | 撤回高峰 | 说错话 / 情绪失控 |
| **P2** | 深夜密集 | 情绪波动期 |

> 🔴 **警告：不要只看消息量。**
> 我曾把某日 3,885 条判为"全库最高密度对话日"，扩读后发现 **80% 是同一张表情包反复发送**，
> 真实文字只有 413 条。
> **`peaks` 命令已经内置了文字占比，占比低的直接排除。**

### 步骤 2 · 扩读

选定锚点后，**前后各扩读几天**。用：

```bash
python3 query.py day 2024-03-15
python3 query.py range "2024-03-15 22:50" "2024-03-15 23:30"
```

**扩读幅度：**

| 情况 | 幅度 |
|---|---|
| 一般 | ± 2~3 天 |
| 有连续事件 | 向后 7~8 天 |
| 找起因 | **向前** |

> 🔴 **必须双向扩读。**
> 我的锚点原本定在 A 日，只往后看了 8 天。后来向前查，才发现**前几天才是真正的起点**，
> 且当时是**对方先求助**——完全颠覆了"一方出问题→一方陪伴"的单向叙事。
> **向后看事情怎么发展，向前看事情怎么开始。只做一半，结论就会错。**

### 步骤 3 · 回扫

写初稿后，**立即用全库检索验证假设**：

```bash
python3 query.py theme 就医      # 用预设主题
python3 query.py kw 自定义,关键词
```

**回扫能推翻扩读时的误判。** 我的两条主要结论都是在这一步被推翻的。

**回扫注意事项：**

| 坑 | 现象 | 处理 |
|---|---|---|
| **高频词噪声** | 搜"聊天记录"得 305 条，其实 173 条是「合并转发」的 XML 残留 | 先看原始命中样本，再统计 |
| **同名实体混入** | 搜人名会带出无关提及 | 看上下文再归类 |
| **时间字段不统一** | 有的记录用字符串 `seq` 排序 | 一律用时间戳排序 |

`query.py` 已内置 XML 残留过滤。

## 五、分析文档怎么写

分两种，**不要混**：

| 类型 | 用途 | 风格 |
|---|---|---|
| **回忆型** | 帮自己/别人快速回忆某段 | 连续散文，**无表格无小标题**，不标时间戳 |
| **分析型** | 做长期追踪、找规律 | 表格 + 精确数字 + 引用 |

**回忆型**的要诀是**低认知负荷**：读者是在回忆，不是在研究。
分表格、加小标题、标满时间戳，都会增加解析成本。

**分析型**必备五节：

1. **结论先行** — 一屏内看完最重要的判断
2. **证据与数字** — 每个判断都要有可核对的数字
3. **推测单独标注** — 明确区分事实与判断
4. **修正节** — 写清"我之前错了，错在哪"
5. **遗留问题** — 未验证的事项单列，不混进结论

## 六、常见错误（血泪清单）

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 只看消息量判定重要性 | 把斗图日当转折点 | 先看文字占比 |
| 2 | 只向后扩读 | 漏掉真正起点 | 双向各扩一次 |
| 3 | 写完不回扫 | 假设当成结论 | 每条线索全库检索 |
| 4 | 高频词不过滤 | 结果九成是噪声 | 先看样本再统计 |
| 5 | **凭记忆写数字** | 生成错误结论 | **跑 verify.py** |
| 6 | 统计不排除异常 sender | 占比分母错 | 分组前先排除 |
| 7 | 混淆两种文档用途 | 反复返工 | 先问清"给谁看、干什么" |
| 8 | SQLite 不加 PRAGMA | 导入慢 5~10 倍 | 三行 PRAGMA 必加 |

## 七、命令速查

```bash
python3 query.py top                # 全库概览（按年/按人）
python3 query.py peaks              # 找异常高值（含文字占比）
python3 query.py silent 3           # 找 >3 天的沉默断点
python3 query.py day 2024-03-15     # 某天全文
python3 query.py range "起" "止"     # 跨天
python3 query.py theme 心理          # 预设主题
python3 query.py themes             # 列出主题
python3 query.py kw 词1,词2          # 自定义检索
python3 query.py stat 2024-03       # 月度统计
python3 query.py hour 2024-03-15    # 小时分布
```

**自定义主题：** 编辑同目录 `themes.txt`，格式 `主题名: 词1, 词2`

## 八、文件说明

| 文件 | 作用 |
|---|---|
| `import_db.py` | JSON → SQLite（改开头的 `SRC`/`DB` 路径即可） |
| `query.py` | 检索工具 |
| `verify.py` | 数字核对（`--init` 固化指纹） |
| `themes.txt` | 主题词配置（可选） |
| `fingerprint.json` | 你的数据指纹（`--init` 后生成） |

## 九、边界与免责

**本方法适合：**

- 个人长期聊天记录（私聊 / 小群），几十万条量级
- 想追踪某个主题（情绪、关系、健康、决策）的长期演变
- 给自己或某个人做时间线回溯

**本方法不适合：**

- 群聊（几百人以上）——噪声比太高，锚点会失效
- 想做"全自动情绪分析"——情绪需要逐句读，脚本只能定位
- 涉及他人隐私的记录——**导出和处理前请确认你获得了当事人同意**

**关于 AI 的局限：**

AI 在长文档处理上会**编造数字**。本文档反复强调 `verify.py`，就是针对这一点。
**任何 AI 给出的统计数字，都应该用脚本复核后再引用。**
