# 03 · 分析方法论

> 这份文档记录一套**处理长期聊天记录的完整流程**，从拿到原始导出文件到产出可读的分析结论。
> 所有内容已做脱敏，示例数据为虚构。
>
> **核心结论先行：不要全量索引。先筛，再锚点，后扩读。**

---

## 一、为什么不能全量索引

假设你有一份 30 万条消息的记录（约 150MB JSON，按每天聊、持续两三年推算）。

**直觉做法**是"全部导入数据库，然后逐条分析"。这个做法有三个问题：

| 问题 | 说明 |
|---|---|
| **信噪比极低** | 日常聊天里 80% 以上是"吃了吗""晚安""哈哈哈"这类无信息量内容 |
| **结论会被稀释** | 你关心的重大事件淹没在几万条日常里，找不出来 |
| **成本失控** | 逐条读一遍，时间上不可行；交给 AI 则远超上下文 |

**正确做法是把"筛选"前置**，只对你真正需要的部分做深度阅读。

---

## 二、六步流程

### Step 0 · 先验证数据，再看内容

**这一步最容易被跳过，也最危险。**

拿到数据后，第一件事不是分析，是**确认数字对得上**。

```bash
python3 tools/verify.py --init          # 第一次：建立数据指纹
python3 tools/verify.py                 # 之后每次：对比指纹，看是否被改过
```

**为什么重要**：分析过程中会反复引用数字（消息总数、占比、某类消息条数）。**一个错误的数字会生成一个错误的结论，然后污染所有引用它的人。**

真实教训：曾把一份统计写成"我方 59.6% / 对方 40.4%"，实际是"60.14% / 39.86%"。原因是**没有排除系统消息（sender='0'）**，而且分母口径不一致。这个错误数字后来被写进报告、又被引用。

**验证清单**（拿笔对一遍）：

- [ ] 消息总数：数据库 `COUNT(*)` vs 导出文件的 `statistics` 字段
- [ ] 双方占比：**必须先排除 `sender='0'`**，再算比例
- [ ] 系统消息数：三个地方的数据要一致（JSON 的 `system:true` 计数、`statistics` 字段、数据库 `system=1` 计数）
- [ ] 时间范围：最早/最晚消息的时间戳
- [ ] 去重是否生效：重复导入一次，总数不应变化

> ⚠️ **一个特别容易犯的错**：用"看起来像文本"的字段判断消息类型。
> 图片消息的 `mtype` 和文本消息**可能都是 `type_1`**，区别在 `hasres` 字段。
> **正确的文本判据是 `hasres=0`，不是 `mtype`。**

---

### Step 1 · 导入数据库

```bash
python3 tools/import_db.py chat.json chat.db
```

**关键点**：导入前设置 PRAGMA 关闭日志和同步，速度能快 5–10 倍。

```python
PRAGMA journal_mode = OFF
PRAGMA synchronous = OFF
PRAGMA temp_store = MEMORY
```

150MB / 30 万条，通常 5 秒内完成。

**表的字段设计**（12 个字段覆盖绝大多数分析需求）：

```
id, seq, ts, tstr, sender, mtype, text, recalled, system, hasres, restype
```

> ⚠️ **`seq` 字段可能是字符串**。按它排序会出错，**用 `ts` 或 `tstr`**。

---

### Step 2 · 筛选（不是索引）

**先做减法。** 这一步决定后面所有工作的效率。

```bash
python3 tools/query.py stat 2024-03      # 月度概览
python3 tools/query.py hour 2024-03-15   # 小时分布
```

**要建立几个"基线认知"：**

1. **总量曲线**——按年、按月看消息量，找出高峰期和低谷期
2. **时段分布**——什么时段在聊，深夜占比多少
3. **消息构成**——纯文本 vs 图片/表情的占比

**关于第 3 点有个陷阱**：某些日子消息量特别高，可能**不是"话多"，而是"斗图"**。

真实教训：曾把某天判为"全库峰值对话日"，后来做构成分析发现 **3,115/3,885 条是图片，占 80.2%**。那天其实是"斗图日"，不是深度对话。

```bash
python3 tools/query.py peaks            # 排名靠前的日子，会标注"刷屏"
```
> `peaks` 命令会同时算"文本占比"，低于 30% 的自动标记为刷屏日。**这个检查必须做**，否则会把斗图日误判为关键日。

---

### Step 3 · 锚点 + 扩读

**这是整套方法的核心。**

不去索引全部内容，而是**锁定少数高价值锚点，然后围绕它前后扩读**。

**怎么找锚点：**

| 信号 | 命令 | 说明 |
|---|---|---|
| 深夜高密度 | `query.py silent` / 按日聚合 | 深度交流通常发生在 23:00–02:30 |
| 长时间停顿 | 按日聚合找空隙 | **但空隙≠事件**，见下方警告 |
| 长消息 | `LENGTH(text)>=80 AND hasres=0` | 系统性表达的标志 |
| 主题峰值 | `query.py kw "关键词"` | 关系、就医、心理等主题线 |

**扩读必须双向。**

> 🔴 真实教训：分析某个锚点时，一开始只**向后**扩读了 8 天。
> 后来**向前**查，才发现真正的起点在锚点**之前 2 天**，而且那晚是**对方先求助**。
> **这完全颠覆了"我方出问题→对方陪伴"的单向叙事。**
>
> **只向前扩读会错过起因，只向后扩读会错过起点。**

建议每个锚点前后各扩 2–8 天，具体看对话密度。

**关于"长沉默"的重要警告：**

长沉默 ≠ 有事件。判断一个空隙是不是事件，必须看两件事：

1. **边界的语气**——沉默前最后一句、沉默后第一句是否带情绪
2. **周边的基线**——如果整段时期都低活跃，那是趋势不是事件

> 真实教训：全库最长的一个 11 天空白，被列为"待分析锚点"。
> 实际读完后发现：**边界两句都是纯日常，周边基线本来就在低位**。
> 真相是**考前冲刺期的正常断联**，而且对方临走前主动交代过原因。
>
> **数字没错（11 天确实是全库最长），但推断错了（最长 ≠ 有事件）。**
> 这种错误比数字错更隐蔽。

---

### Step 4 · 主题回扫（防幻觉）

**写完初稿后，必须回到全库做关键词搜索，验证或推翻自己的假设。**

这一步是**强制**的，不是可选的。

```bash
python3 tools/query.py kw "关系"
python3 tools/query.py kw "就医"
```

**回扫能发现什么：**

- **推翻结论**：以为自己找到了转折点，回扫发现同类对话出现过多次，不是转折
- **发现遗漏**：某个主题在别处还有延续，初稿漏了
- **校准时间线**：某句话是第一次出现，还是重复出现

> 真实教训：初稿判定"某次道歉没有回应"，回扫后发现**对方次日早上就完整接住了**（还主动提议打电话）。初稿漏读了次日上午的记录。
> **回扫之后，整个结论从"没人接"改成了"接了，但事后没复盘"。**

---

### Step 5 · 输出

**先问用途，再决定格式。** 同一份记录，"研究报告"和"个人备忘"是两种完全不同的东西。

| 用途 | 形态 | 特征 |
|---|---|---|
| **给别人看 / 研究** | 分析报告 | 表格、分点、有结论 |
| **自己快速回忆** | 备忘 | 连续叙述、无表格、无小标题、无评价 |

**两者绝不能混。** 混了就会出现"想快速回忆，拿到的却是一份议论文"。

`presets/提问预设.md` 里有 7 个预设，覆盖常见用途。**如果只能记一条，记这段话：**

```
输出要求：
- 不要表格，不要小标题，不要分点罗列
- 按时间顺序连续叙述，事件用整段话写
- 时间戳不用标，除非时间差本身有意义（比如犹豫、沉默、隔了很久才回）
- 只写事实，不写评价和总结
- 如果是你的推测，单独标出来
```

## 三、几个可复用的分析视角

### 3.1 相对变化 > 绝对词表

**情绪词（"累""不想""怕""对不起""为什么"）每天都会出现，没有区分度。**

用关键词表去找情绪，命中率极高但信息量极低。

**更有用的做法是看"相对变化"：**

- 某个词的**频率随时间的走势**（是上升还是下降）
- **特定组合**同时出现的日子
- **长消息/深夜消息**的年度变化（这比单个词准确得多）

### 3.2 区分"当下回应"和"事后复盘"

在分析冲突时，这两件事要**分开评估**，它们经常结果相反：

| 环节 | 常见情况 |
|---|---|
| ① 当下回应 | 多数时候是接住的（安慰、道歉、提议） |
| ② 事后复盘 | 很少发生 |

**很多关系的模式不是"表达没人接"，而是"表达了、也被回应了，但事件从不在平静时被重新提起"。**

**复盘的判据**（需同时满足）：
1. 提及该事件（"昨晚""之前说的"）
2. **且**内容是对该事件的重新讨论、总结或承诺
3. **且**不是单纯的情绪延续

**排除项**：单纯的"我也难受"、表情、无关的梦、日常事务。

> ⚠️ 关键词检索对"是否复盘"的**命中率很低**（因为复盘往往不用"昨晚""之前"这类词）。
> 所以**"未命中"是弱证据，必须人工确认**。

### 3.3 撤回消息的价值在"行为"不在"内容"

**重要前提**：多数导出工具**不保存撤回消息的正文**，只留一个占位符（如 `[1]`）。
**内容通常是永久不可恢复的**——任何声称能还原创作者都是在编。

**但行为痕迹全在**，而且信息量不小：

- **撤回间隔**：距上一条消息多久。间隔中位数很小（如 14 秒）说明是"手快"而非"深思"
- **是否被追问**：撤回后对方有没有问"你撤了什么"
- **时段分布**：深夜撤回往往对应"打出来又删掉"

> 观察：如果对方的**追问率极低**（如仅 1%），那说明**撤回是一种双方都不处理的默契**。

### 3.4 注意"命题"和"状态"的区别

分析长期关系时，一个有用的区分：

| 类型 | 例子 | 能否被讨论 |
|---|---|---|
| **命题** | "我会对你失去耐心" | ✅ 可被驳斥、可被论证 |
| **状态** | "我想要被爱" | ❌ 无法反驳，只能感受 |

**能被"复盘"的，往往是命题；不能被复盘的，往往是状态。**

如果一方习惯**用理性方式处理情绪**，那么他可能**只会回收那些能被打分的命题**，而把状态类表达直接略过。这个模式值得单独验证。

## 五、常见坑（按严重程度排序）

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | **不验证数字就开始分析** | 错误数字污染所有结论 | Step 0 必做 |
| 2 | **用 `mtype` 判断文本消息** | 把图片当日志，统计全错 | 用 `hasres=0` |
| 3 | **只用 `seq` 排序** | `seq` 是字符串，顺序错乱 | 用 `ts` / `tstr` |
| 4 | **扩读只做单向** | 错过起因或起点 | 前后各扩 2–8 天 |
| 5 | **把"高消息量"当"深度对话"** | 斗图日被误判为关键日 | 做构成分析，看文本占比 |
| 6 | **把"长沉默"当"有事件"** | 误判出不存在的事件 | 查边界语气 + 周边基线 |
| 7 | **`GROUP BY` 和 `WHERE` 顺序搞错** | 聚合结果整个失真且不报错 | 先过滤行，再聚合 |
| 8 | **写完不回扫** | 结论里留下幻觉 | Step 4 强制 |
| 9 | **混淆"分析报告"和"备忘"** | 用途完全不匹配 | 先问用途 |

## 七、数据准备备忘

**导出格式首选 JSON。** 相比 txt / html / excel：

- 字段结构化（发送者、时间戳、消息类型分开），不需要正则解析
- 消息类型可判断（能区分文本、图片、系统消息）
- 便于导入数据库
- **txt 会丢失发送者和时间戳的结构，"谁在什么时候说的"要重新解析，容易出错**

**关于撤回消息**：如果在意这部分内容，**需要增量导出**——撤回窗口可能只有几分钟。
等几年后再导出，正文一定拿不到了。

**隐私提醒**：全量聊天记录是高度敏感数据。
**不要放进公开仓库，不要上传到网盘直链**，本地处理完即止。
