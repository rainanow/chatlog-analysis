# 长期聊天记录分析工具包

把两三年的聊天记录（几十万条）理成一条能读的线。

> **核心思路：不要全量索引。先筛，再锚点，后扩读。**

---

## 这是什么

一套处理长期聊天记录的**本地流程**，解决三个具体问题：

1. **数据太大** —— 30 万条消息、150MB JSON，不能逐条读，也不该全丢给 AI
2. **信噪比低** —— 80% 以上是日常废话，重大事件淹没其中
3. **输出错位** —— 想快速回忆，却拿到一份议论文

包含**可运行的工具** + **一套分析方法论** + **提问预设**。

---

## 快速开始

```bash
# 0. 先验证数据完整性（最容易被跳过，也最危险）
python3 tools/verify.py --init

# 1. 导入数据库（150MB 约 5 秒）
python3 tools/import_db.py chat.json chat.db

# 2. 建立基线认知
python3 tools/query.py stat 2024-03       # 月度概览
python3 tools/query.py hour 2024-03-15    # 时段分布
python3 tools/query.py peaks              # 高密度日（自动标记刷屏日）

# 3. 检索
python3 tools/query.py day 2024-03-15                        # 某天全文
python3 tools/query.py kw "关键词"                            # 全库关键词检索
python3 tools/query.py theme 关系                             # 预设主题检索
python3 tools/query.py range "2024-03-15 22:50" "2024-03-16 02:00"  # 时间区间
```

> 数据库不在脚本同目录时，用环境变量指定：
> `CHAT_DB=/path/to/chat.db python3 tools/query.py top`

## 方法论要点

### 六步流程

| 步骤 | 做什么 | 关键点 |
|---|---|---|
| **0** | 验证数据 | 数字对不上，后面全白做 |
| **1** | 导入数据库 | 关掉日志和同步，快 5–10 倍 |
| **2** | **筛选**（不是索引） | 先做减法，建立基线认知 |
| **3** | **锚点 + 扩读** | 锁定高价值点，**前后双向扩读** |
| **4** | **主题回扫** | 强制步骤，验证或推翻自己的假设 |
| **5** | 按用途输出 | 分析报告 ≠ 个人备忘，绝不混用 |

### 三个反直觉的结论

**① 高消息量 ≠ 深度对话。**
某天 3,885 条消息里 80.2% 是图片。那是"斗图日"，不是关键日。
**做分析前必须查文本占比。**

**② 长沉默 ≠ 有事件。**
全库最长的 11 天空白被当成"待分析锚点"。读完发现边界两句都是纯日常、周边基线本来就在低位——真相是考前冲刺期的正常断联。
**判断空隙，要看边界语气 + 周边基线，不能只看长度。**

**③ 表达"被回应了"，不等于"被复盘了"。**
很多关系的模式不是"说了没人理"，而是**"说了、也被安慰了，但事件从不在平静时被重新提起"**。

### 一条通用尾巴

如果只能记住一件事，记这段（用在所有"自己想要回忆"的场景）：

```
输出要求：
- 不要表格，不要小标题，不要分点罗列
- 按时间顺序连续叙述，事件用整段话写
- 时间戳不用标，除非时间差本身有意义
- 只写事实，不写评价和总结
- 如果是你的推测，单独标出来
```

## 坑清单（按严重程度）

| # | 坑 | 对策 |
|---|---|---|
| 1 | 不验证数字就开始分析 | `verify.py` 必做 |
| 2 | 用 `mtype` 判断文本消息 | 用 **`hasres=0`**（图片的 mtype 可能也是 `type_1`） |
| 3 | 只用 `seq` 排序 | `seq` 是字符串，用 `ts` / `tstr` |
| 4 | 扩读只做单向 | 前后各扩 2–8 天 |
| 5 | 把高消息量当深度对话 | 查文本占比 |
| 6 | 把长沉默当有事件 | 查边界语气 + 周边基线 |
| 7 | `GROUP BY` 与 `WHERE` 顺序错 | 先过滤行，再聚合 |
| 8 | 写完不回扫 | 主题回扫是强制的 |
| 9 | 混淆分析报告与备忘 | 先问用途 |

## 数据格式

**首选 JSON 导出**（QQChatExporter / 类似工具均可）。

相比 txt / html / excel，JSON 的优势：
- 字段结构化，不需要正则解析
- 能区分消息类型（文本 / 图片 / 系统）
- 便于导入数据库

**txt 会丢失发送者和时间戳的结构**，"谁在什么时候说的"要重新解析，容易出错。

### 关于撤回消息

**多数导出工具不保存撤回消息的正文**，只留一个占位符（如 `[1]`），**内容永久不可恢复**。

如果这部分对你重要，**需要增量导出** —— 撤回窗口可能只有几分钟。等几年后再导出，正文一定拿不到了。

## 隐私提醒

**聊天记录是高度敏感数据。**

- ❌ 不要把原始的 `.json` / `.db` 放进公开仓库
- ❌ 不要上传到网盘直链
- ✅ 分析结论如果含真实对话原文，**发布前做脱敏**
- ✅ 本仓库内所有示例均已脱敏，可作模板直接改用

建议在项目根目录加 `.gitignore`：

```gitignore
*.json
*.db
*.db-journal
*.csv
!themes.txt
```
