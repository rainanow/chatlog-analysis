# ChatLog Analysis — Portable Agent Spec

> 一份让 LLM Agent 自主完成聊天记录事件分析的规范。
> 输入任意平台的两人对话导出文件，输出可追溯、带强度分级的事件报告。

**规格文件**：[`CHATLOG_AGENT_SPEC_通用版.md`](./CHATLOG_AGENT_SPEC_通用版.md) · 1,079 行 · 12 节

---

## 这个 Spec 解决什么问题

让 Agent 分析聊天记录，绝大多数实现会掉进同一个坑：**用统计量代替阅读**。

"消息量骤降 = 关系降温"、"情绪词密度 = 冲突强度"——这类信号听起来合理，但在真实数据上**全部失效**。本 Spec 的 §5.1 记录了 **9 个已被实测证伪的信号设计**，以及失效的根本原因：

> 「说得多 / 说得长 / 一个人在说」这件事，在关系好和关系差的时期**同样发生**。

更反直觉的是方向性问题：冲突日的对话**回复更长**（5 字 vs 3 字）、**回复更快**（P90 延迟 114s vs 214s）。**用"冷漠度"指标找冲突，方向本身是反的。**

所以本 Spec 的立场很明确：

```
统计信号 → 只用于【减量】（30 万条 → 50 个候选）
语义原词 + 结构性缺失 → 用于【判定】
Agent 通读原文 → 用于【定性】
```

**读者应默认：任何"让模型直接读聊天记录然后总结"的做法，产出的都是幻觉。**

## 适用与不适用

| | |
|---|---|
| ✅ 双人对话（一对一） | ❌ 群聊（"对方"不是单一主体，语域法需重构） |
| ✅ 有文本 + 发送者 + 时间戳 | ❌ 单人日志 / 邮件（无"回合"结构，接话分析失效） |
| ✅ 任意平台、语言、格式 | ❌ 样本 < 1 万条（结构性缺失无统计意义） |
| ✅ 分析者是其中一方 | ❌ 分析者是完全第三方（无法使用内部因果） |

**数据规模建议**：≥ 5 万条时价值最高。低于此规模，语义原词扫描仍有效，但"事后证词反推"（§5.5）和"承诺半衰期"（§5.9）需要足够的跨度才能成立。

## 快速开始

### 1. 准备输入

任意一种即可，不需要预处理：

- 单文件（JSON / CSV / TXT / HTML / XML / SQLite）
- 目录（多个分片）
- 已知格式无需说明，Spec §3.2 会先探测

### 2. 交给 Agent

```
读 CHATLOG_AGENT_SPEC_通用版.md，按 §0 读取协议执行。
输入文件：<你的路径>

注意：
- §3 接入层是第一步，先完成格式探测和字段映射再继续
- §3.5 的字段映射表产出后请展示给我确认
- §4 污染检测未完成前不要进入分析
```

### 3. 预期流程

```
§3 接入层        任意格式 → IR（统一中间表示）      ← 决策点：字段映射需人工确认
§4 污染检测      量化占位符噪声 / 机器消息 / 挂机日   ← 卡点：未完成不得继续
§5 判定规则      28 条规则（R-01 ~ R-28）
§6 SOP          首次运行 9 步 / 常规轮次 8 步
§7 输出 Schema   固定结构的报告
```

### 4. 验收标准

Agent 产出应包含**必需项**：

```yaml
- field_mapping.yaml          # 字段映射表（§3.5）
- contamination_report.yaml   # 污染检测报告（§4.6）
- 报告/<轮次>.md               # 含 Front Matter（§7.1）
- 事件清单（YAML 结构）        # 每个事件至少 2 条证据行
- 噪声候选章节                 # ⚠️ 缺失 = 本轮报告无效
```

**逐项核验**：`噪声候选章节` 和 `对既有结论的修正` 是强制的。缺任何一个，说明 Agent 跳过了流程。

## 设计要点

### 接入层：为什么必须抽 IR

原实现直接绑定某一种导出格式的字段名。换平台即失效。

Spec §3.1 定义了一张唯一的中间表：

```sql
CREATE TABLE msg (
    id TEXT, seq INTEGER, ts INTEGER,   -- ts 强制毫秒
    tstr TEXT,                           -- 统一 YYYY-MM-DD HH:MM:SS
    sender TEXT,                         -- 'self' / 'peer' / 'system'  ← 已归一化
    mtype TEXT, text TEXT,
    recalled INTEGER, system INTEGER,
    hasres INTEGER, restype TEXT
);
```

**`sender` 归一化为三值**是关键决策：原始昵称不进入 IR，所有下游工具无需关心数据来源。

**纯文本格式的续行识别**：不处理续行会把长消息逐行拆开，是 TXT 导入最常见的错误。§3.3.2 给了两阶段解析策略（先探测头部正则，再用续行规则合并）。

**未知格式不猜**（§3.3.4）：字段映射错误会导致"分析看起来完全正常但全错"。Spec 强制 Agent 停下来索取样本。

### 污染检测：跨平台正则

占位符判定必须跨平台。实测对比：

| 输入 | 原实现 | 通用实现 |
|---|---|---|
| `[图片: abc.png]` | ✅ | ✅ |
| `[表情63]` × N | ✅ | ✅ |
| `[Photo]` | ❌ 判为真实文本 | ✅ |
| `<Media omitted>` | ❌ | ✅ |
| `[Sticker]` | ❌ | ✅ |
| `[图片]我们要不要聊聊` | ❌ | ✅ 剥离后保留真实文本 |

原实现只有中文词表，非中文平台的记录进去**字数统计会完全虚高**。

通用版正则（§4.1）同时覆盖中英文标记，并附带**回测测试集**——扩展词表后必须全部通过。

### 硬约束而非建议

Spec 用 HARD FAIL 而非"建议"来表达边界。例如：

```
F-07  不得跳过噪声候选章节。缺失 = 本轮无效
F-09  不得跳过 §4 污染检测直接分析。未检测污染 = 全部数字作废
```

原因很实际：**Agent 换窗口后最容易做的是跳过前置步骤直奔结论**。软性表述拦不住。

### 噪声记录为什么强制

多个候选日会在不同轮次被反复扫到。不记录，每轮都要重判一次。

更重要的是**噪声类型会演化**。实际项目中观测到的类型从"普通误命中"演进到：拟声词/梗、影视台词、游戏 bug 引发的情绪表达、超高条数+极低字数的挂机日。

每发现一类新噪声就追加到 §4.4 词典——**这是省时间最多的一条。**

## 已知局限

读 Spec 前应知道这些：

| 局限 | 说明 |
|---|---|
| **撤回内容不可恢复** | 导出源即占位符，不要尝试 |
| **语音/图片内容不可读** | 只有文件名 |
| **对方主动不说的事无法从数据得知** | 只能靠事后证词（§5.5）反推 |
| **边界定义不在数据里** | "算不算一次冲突"存在于人的认知 |
| **规则需要本地化** | §5.4 六语域、§5.7 结构雷点、§5.8 交互模式必须从数据重新识别，不得套用 |
| **逐日通读不可省略** | 本 Spec 不承诺"全自动"。规模越大，人工判定成本越高 |

## 使用建议

**首次运行**：先只跑 §3 + §4，确认字段映射和污染率无误，再进入分析。这两步的产物是后续一切的基础。

**分轮推进**：建议每轮 3~4 个月。每轮产出独立报告，并更新覆盖状态表（§11.1）。盲区必须显式标注规模和条数。

**保留修正记录**：§7.3 强制要求每轮报告包含"对既有结论的修正"章节。实际项目中同一结论被修正过四次——**密度结论极易错**。

**不要把本项目的历史结论当基线**：Spec §5.7 / §5.8 保留的案例标注为"示例，非通用"。它们是识别方法的演示，不是判定标准。

## 隐私

Spec §10 定义了脱敏规则，其中一条与常见直觉相反：

```
按识别力排序（这是脱敏最常见的错误来源）：

  1. 具体日期      风险 极高   → 平移为相对序号
  2. 地名/机构名   风险 极高   → 替换为类型描述
  3. 账号/ID       风险 高     → 删除
  4. 称呼          风险 低     → 替换为 self/peer
  5. 原话引用      风险 低     → 保留（是核心资产）
```

**多数人把称呼当重点，把日期当"不影响隐私的上下文"——恰好反了。** 原话是资产，日期才是风险。

⚠️ 即使正文脱敏，若保留原始日期索引仍可被反向定位。**脱敏要连索引一起做。**

## 来源

规格中的判定规则、污染分类、反模式清单，来自对一份 **1,200 天 / 306,763 条**的真实双人对话的 11 轮迭代分析。其中：

- 9 个信号设计经过实测被证伪
- 关键词匹配的误报率实测约 **50%**
- 原始字数中 **57.9%** 是占位符噪声
- 同一密度结论被修正 4 次

**Spec 里最有价值的部分是被证伪的条目**——成功经验未必能复用，但踩过的坑一定能省时间。
